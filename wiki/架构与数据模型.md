# 架构与数据模型

本文覆盖：分层规则、包结构、SQLite 双库与表结构、并发与备份、配置文件、选手/队伍数据模型。

---

## 1. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  数据导入（本地 / CLI / Web 上传）                              │
│  raw/（人工投放 + import 写回归档）──import──▶ SQLite          │
│  保留 raw/ 作为可复现、可 diff、可进 Git 的数据源                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  运行时（服务器）                                              │
│  Caddy ──reverse_proxy──▶ Reflex（FastAPI + WebSocket）       │
│  Python 常驻    SQLite（WAL）                                 │
│  Rating / 榜单为运行时按需计算，无预生成文件                     │
└─────────────────────────────────────────────────────────────┘
```

与早期「静态站 + JSON 流水线」方案的本质区别：线上有常驻 Python 进程和数据库，交互操作不依赖 CLI。

### 1.1 两条硬性分层规则

- **`xcpc_core` 绝不 `import reflex`** —— 业务层脱离 web 可运行，CLI、pytest、未来定时任务都依赖此保证
- **`xcpc_web` 绝不写 SQL，也不承载业务规则** —— State 只做「读表单 → 调 `xcpc_core` → 转视图模型 → 写 state var」

违反任一条，业务逻辑就会与框架绑死，后续换框架或加 CLI 入口都要重写。

### 1.2 技术选型

| 模块 | 选型 |
|------|------|
| Web 框架 | Reflex **0.9.7（锁版本）**，Python 全栈，编译 React SPA |
| 组件包 | `reflex-components-core` / `-lucide`（独立版本，`uv sync --extra web`） |
| 认证 | `reflex-local-auth` 0.5.0 |
| 数据库 | SQLite（WAL 模式），双库：core 业务 + web 认证 |
| 数据模型 | Pydantic（DTO）+ SQLAlchemy 2.0（ORM），显式互转 |
| 包管理 | `pyproject.toml` 统一打包（无 PYTHONPATH hack），`uv` + `uv.lock` |
| Python | 3.13（`.python-version` 锁定） |

### 2.1 CRUD 模块六件套

`player` / `team` / `tier` 采用完全一致的模式，新增 CRUD 模块照抄：

| 文件 | 职责 |
|------|------|
| `models.py` | Pydantic DTO：`XxxBase` / `XxxCreate` / `XxxUpdate` / 实体 + 校验器 |
| `store.py` | SQLAlchemy repository；DTO↔ORM 转换在 store 边界 |
| `service.py` | 业务逻辑（唯一约束、ID 生成、筛选）；**写路径在此 bump data_version** |
| `api.py` | **对外唯一读写入口**（facade），CLI 与其他子模块都从这里导入 |
| `cli.py` | argparse 命令行（console_scripts：`xcpc-player`、`xcpc-team`） |
| `exceptions.py` | 模块基础异常 + 子类，供 UI 直接展示消息 |

### 2.2 DTO 与 ORM 分离

领域对象用 **Pydantic DTO**（`models.py`），数据库层另建 **SQLAlchemy ORM 表**（`xcpc_core/db/tables.py`），两者显式互转。

- 理由：ORM 实例渗进 service 层会把 session 生命周期问题扩散各处（detached instance、懒加载越界），也污染业务校验
- 收益：service 层可单测、事务边界清晰（对 SQLite 锁行为也是加分项，见 §5.2）

## 3. 数据流

```
data/raw/（人工投放 + import 写回归档，可 diff、可进 Git）
        │
        ▼ import（xcpc_core.importer.*：raw 归档 + SQLite 双写）
        ▼ SQLite（data/db/xcpc.db，运行时数据源）
        ▼ Rating 事件生成（rating.events）→ 重放（rating.replay）
        ▼ 榜单聚合（board，data_version 进程内缓存）
        ▼ Reflex 页面（State 直调 core API）
```

- 数据流**单向**：`raw → DB`；反向只产出备份，不回写 raw
- 原 `data/processed/` 中间层已废弃（职责由 SQLite 取代）
- 榜单不预生成文件：筛选条件为服务端 state var，切换即重算（`mode × period × data_version` 为缓存 key）

## 4. 数据库

### 4.1 双库

| 库 | 内容 | 谁定义 |
|----|------|--------|
| `data/db/xcpc.db` | core 业务 20 张表 | `xcpc_core/db/tables.py`（纯 SQLAlchemy） |
| `data/db/xcpc_web.db` | 认证：`localuser` / `localauthsession` / `userprofile` / `bindingrequest` | `reflex-local-auth` + `xcpc_web/states/auth_models.py`（SQLModel） |

> 认证是纯 web 层关切（`xcpc_core` 不感知用户与角色）。跨库的「选手已被他人绑定」等唯一性校验在 service 层完成。
> 认证库**不在 alembic 迁移体系内**（SQLModel 独立 metadata，`create_admin.py` 建表）；若将来动它需单独收编。

### 4.2 core 表清单（20 张）

| 表 | 主键 | 关键列 / 约束 |
|----|------|--------------|
| `player` | `id` str（p001） | `handle` UNIQUE；`grade`（0=未设置）；`status`（probation/active/retired/left） |
| `ojaccount` | 自增 | FK player；**UNIQUE(platform, handle)** |
| `playeralias` | 自增 | FK player；UNIQUE(player_id, alias) |
| `team` | `id` str（t001） | `member_key` UNIQUE+INDEX（p001\|p002\|p003）；`size` |
| `teammember` | 自增 | FK team、player；`seat` |
| `teamalias` | 自增 | FK team；队名历史 |
| `tier` | 自增 | `name` UNIQUE；`coefficient`（积分/排名系数）；`sort_order` |
| `awardlevel` | 自增 | `name` UNIQUE；`base_points`（奖项基线分） |
| `contest` | `id` str | **统一比赛**：`format`(icpc\|ioi) × `entity`(player\|team) × `tier_id` + `scoring`/`counts_for_points`/`counts_for_ranking`/`allow_claims` |
| `standing` | 自增 | FK contest；`rank` 可空（award_only 行）；award/solved/penalty/score |
| `standingmember` | 自增 | FK standing、player |
| `pointsclaim` | 自增 | FK contest/player/team；`value`/`rank`/`award` 可空互补；部分唯一索引（驳回后可重提） |
| `pointsentry` | 自增 | FK contest；双 owner 流水（player + team_context）；`payload_json` 快照 |
| `meta` | `id`=1 | `data_version`（榜单缓存失效）、`rating_algorithm` |
| `auditlog` | 自增 | 故意不加外键（用户删除后审计保留） |
| `importbatch` | 自增 | `status`（staged/confirmed/discarded）、`payload_json` |
| `ratingevent` | 自增 | `event_id` UNIQUE（派生表，**当前无写入方**，见下） |
| `ojcontest` / `ojcontestresult` / `ojsnapshot` | — | OJ 数据源三表，**有表无代码** |

**关于 `ratingevent`（空表）**：榜单与选手历史改由 `rating/events.build_events_from_contests()` **每次从 contest/standing 实时派生事件对象**（不落库），故该表已无写入方，真库中为空表。代码中仅剩 `contest/store.py::delete()` 的清理逻辑（按 `{contest_id}#` 前缀删除残留行）。表保留是为将来 OJ 数据源复用旧逐事件路径；若 OJ 立项不采用，可考虑删除。

### 4.3 建表与迁移

- **schema 由 alembic 管**：迁移脚本在 `xcpc_core/db/migrations/`（基线 `0001_baseline` 16 张表 → `0002_points` → `0003_unify_contest` 比赛统一化 → `0004_atcoder_v1` 算法升版，head = `0004`）
- 运行时唯一入口 `xcpc_core.db.migrations.run_migrations`：全新库 `upgrade head` 建表；alembic 引入前的存量库检测到 `meta` 表已存在且无 `alembic_version` 自动 `stamp head`，均幂等
- `env.py` 用 `render_as_batch=True`（SQLite ALTER 受限，加列/改列走 batch）

> **注意**：运行时连接 `PRAGMA foreign_keys=ON` 且**事务内 pragma 是 no-op**——重建式迁移须先 stash 数据、按「子表→父表」drop 再回插（`0003` 即此模式），不能直接 rename/drop 被引用的父表。

- **新增迁移**：`uv run python -m xcpc_core.db.migrations.revision -m "..."`（autogenerate，前提本地库已升到 head），**生成后必须人工核对再提交**
- 改 `tables.py` 不写迁移会被漂移守护测试（`test_models_match_migrations_no_drift`）拦下
- **一次性灌数据**：`uv run python -m xcpc_core.db.migrate` —— 先 `run_migrations` 建/升 schema，再读 `raw/players/roster.json`、`raw/teams/roster.json`、`raw/{formal,contests}/*.json`，**幂等**（按主键 upsert）
- **测试内存库不走 alembic**（alembic 自开连接，`:memory:` 建完即丢），conftest 直接 `Base.metadata.create_all`；schema 一致性由漂移守护测试保证

## 5. SQLite 并发与运维

### 5.1 三件事同时做到，缺一不可

SQLite 允许多个并发读，但**同时只能有一个写**。要在 Web 场景下不报 `database is locked`：

| # | 措施 | 作用 |
|---|------|------|
| 1 | **WAL 模式** | 读不阻塞写（持久化，设一次生效） |
| 2 | **busy_timeout** | 撞锁时等待重试而非立刻抛错 |
| 3 | **短事务** | 不在持有写锁时做慢活（xlsx 解析、Rating 重算不放写事务） |

**WAL 单独不够**（实测：仅 WAL 不设 timeout，6400 次操作仍 7 次锁错误；WAL + 1s busy_timeout 为 0）。实现见 `xcpc_core/db/session.py`——PRAGMA 挂在 `connect` 事件**逐连接执行**，`journal_mode` 除外（持久化在库文件）。`foreign_keys=ON` 也要逐连接设：SQLite 默认不强制外键。

### 5.2 三个容易踩的坑

- **`check_same_thread=False` ≠ 连接可并发使用**：连接池线程安全，`Session` 对象不是——不要跨线程共享 session
- **ORM 会让锁问题更严重**：Session 默认在事务中运行，autoflush 会在 SELECT 前先发 DML。DTO/ORM 分离让事务边界更容易看清（§2.2 的附带理由）
- **长事务是最大的隐藏杀手**：导入解析用 `ImportBatch` 暂存、确认才短事务落库，正是为此

### 5.3 规模与单进程

- 写操作量级是「admin 偶尔导一场比赛、队员偶尔改 OJ 账号」，WAL + busy_timeout 完全够用；真不够时 `db_url` 换 Postgres，`xcpc_core` 一行不改
- **单进程约束**：Reflex State 存在进程内存里（按 client token 索引），多 worker 会让同一用户落到不同进程。**不要加 `--workers`**；这同时保证 SQLite 只有一个写进程

### 5.4 备份

```cron
30 4 * * * sqlite3 /opt/xcpc-rating/data/db/xcpc.db ".backup '/var/backups/xcpc-$(date +\%F).db'"
```

用 `.backup` 而非 `cp`（对正在写入的库安全）；`data/raw/` 已在 Git，本身就是一份可追溯冷备。

## 6. 配置文件（`data/config/`）

### 6.1 `contest_weights.yaml`

- `formal_types`：正式赛 `contest_type` → 权重（基准 100，允许超基准）。已登记 17 种：区域赛/全国赛 100、线上赛 90、邀请赛 80、全国性其他赛事 75–80、省赛 70、校赛 50–60。**未登记的 `contest_type` 在导入时直接报错**
- `training_divisions`：div1+2=100、div1=95、div2=70、div3=60
- 本文件是「类型 → 等级标签/系数」的**权威种子**：迁移 `0003` 与正式赛导入的 tier 自动建档都以它为准（系数 = weight/100）；等级本身的增删改在管理端 `/admin/tiers`（`tier` 表是运行时权威）
- `oj`：`contest_default`=40、`practice_default`=20 —— **代码尚未读取该段**（OJ 数据源未立项）

### 6.2 `school.yaml`

本校 Organization 精确匹配名 + 自动建档默认 `grade`。导入时以精确匹配过滤本校队伍；`auto_create_players` 场景按 `player_defaults.grade` 建号。

### 6.3 `rating_params.yaml`（可选）

`/admin/rating` 试算页点「应用」后生成，存 AtCoder 公式参数。**文件不存在时用内置默认值**。字段见 [Rating与积分](Rating与积分)。

## 7. 选手与队伍

### 7.1 选手字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | str | 校内 ID，`p001` 起全局递增（`PlayerStore.next_id()`），可显式指定 |
| `name` | str | 真实姓名，**admin-only**（影响导入时的选手匹配） |
| `handle` | str \| None | 校内简称，UNIQUE；自助字段 |
| `grade` | int | 入学年；**`0` 表示未设置**（榜单显示「未设置」） |
| `status` | enum | 状态机，见 §7.2 |
| `oj_accounts` | list[OJAccount] | `platform`（codeforces/atcoder/luogu/nowcoder）+ `handle`，**UNIQUE(platform, handle)** |
| `aliases` | list[str] | 曾用名/英文名，UNIQUE(player_id, alias)，导入匹配也用它 |
| `created_at` / `updated_at` | date | |

### 7.2 状态机

| 状态 | 语义 | 榜单行为 |
|------|------|----------|
| `probation` | 预备队员（入队考核中） | 打过比赛即可上榜 |
| `active` | 现役 | 正常上榜 |
| `retired` | 退役 | **保留**档案、历史成绩与 Rating，上榜并带退役标记 |
| `left` | 离队（软删除） | **不出现在榜单**，数据保留 |

流转规则：

- `probation → active`：入队（`mark_active`，**仅 probation 可调用**，防止退役/离队选手被「入队」复活）
- `active → retired`（`mark_retired`）、`active → left`（`mark_left`）
- 其他状态变更走 `update_player` 显式修改（admin 权限）
- `left` 是软删除；`delete_player` 为**物理删除**（连带 oj_accounts / aliases）

### 7.3 字段级权限

| 字段 | 绑定 member 改自己 | admin |
|------|:---:|:---:|
| `oj_accounts` / `aliases` / `handle` | ✅ | ✅ |
| `name` / `grade` / `status` | ❌ | ✅ |

admin-only 的原因：`name` 影响导入匹配、`grade` 影响榜单分组、`status` 决定榜单可见性——让本人修改等于让被统计者改统计口径。自助编辑入口在 `/profile`。

### 7.4 唯一性与校验

唯一性由 DB 约束兜底（`handle` UNIQUE、`(platform, handle)` UNIQUE、`(player_id, alias)` UNIQUE），service 层捕获 `IntegrityError` 转成 `PlayerValidationError`，消息可直接展示到 UI（如「OJ 账号已绑定其他选手」）。

### 7.5 队伍身份规则

- **队伍身份由队员集合决定，与队名无关**：`make_member_key` = 排序后 `"p001|p002|p003"`，UNIQUE+INDEX
- 同名队员不同队名 → **同一支队伍**（新队名追加进 `aliases` 队名历史）
- 换员（任一队员变动）→ `member_key` 变化 → **新队伍**
- 1–3 人；成员写入 `teammember`（含 `seat`）

> Web 端编辑队伍遵循 `skill/team-manage/SKILL.md`：**只追加别名，不原地修改 members**；换员请新建队伍。

### 7.6 API 速查

**选手**（`xcpc_core.player.api`）：

| 函数 | 说明 |
|------|------|
| `list_players(include_left, status, grade, store)` | 列表 + 筛选 |
| `get_player(player_id, store)` | 单查，不存在抛 `PlayerNotFoundError` |
| `find_by_name(name, grade, store)` | 按姓名或别名（导入匹配用） |
| `find_by_oj(platform, handle, store)` | 按 OJ 账号查 |
| `create_player(data, today, store)` | 新建（含唯一性校验、ID 生成） |
| `update_player(player_id, data, today, store)` | 更新（仅提交的字段生效） |
| `delete_player(player_id, today, store)` | 物理删除 |
| `mark_left / mark_retired / mark_active(player_id)` | 状态流转 |

**队伍**（`xcpc_core.team.api`）：`create_team(TeamCreate(members=...))` / `update_team` / `delete_team` / `list_teams` / `find_by_member_key` / `find_by_members` / `add_alias`。冲突预检：按队员集合建重队时提示已存在的队。

**session 生命周期**：facade 未注入 `store` 时自建短事务 session 并在 finally 关闭（**注入 store 则由调用方管理**）——这是修复「连接池耗尽」后的约定，测试与 Web 注入 store 时不得泄漏。

### 7.8 与导入的联动

- 导入解析队员姓名时按 `name`/`aliases` 匹配；歧义或未匹配进 `unmatched`，**不盲目建号**
- staged 流程中管理员对未匹配选手逐个决议「新建 / 指定已有」，新建走 `create_player(commit=False)` 并入确认大事务
- 队伍按 `member_key` 查找或创建，队名追加进 `aliases`
- 详见 [比赛与导入](比赛与导入)
