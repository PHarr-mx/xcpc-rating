## 1. 架构总览

```
┌─────────────────────────────────────────────────────────────┐
│  数据导入（本地 / CLI / Web 上传）                              │
│  raw/（人工投放 + import 写回归档）──import──▶ SQLite          │
│  保留 raw/ 作为可复现、可 diff、可进 Git 的数据源                │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  运行时（服务器）                                              │
│  Caddy ──reverse_proxy──▶ Reflex（FastAPI + WebSocket）       │
│  Python 常驻  ✅  SQLite（WAL） ✅                             │
│  Rating / 榜单为运行时按需计算，无预生成文件                     │
└─────────────────────────────────────────────────────────────┘
```

与早期「静态站 + JSON 流水线」方案的本质区别：线上有常驻 Python 进程和数据库，交互操作不依赖 CLI。

### 1.1 两条硬性分层规则

- **`xcpc_core` 绝不 `import reflex`** —— 业务层脱离 web 可运行，CLI、pytest、未来定时任务都依赖此保证。
- **`xcpc_web` 绝不写 SQL，也不承载业务规则** —— State 只做「读表单 → 调 `xcpc_core` → 转视图模型 → 写 state var」。

违反任一条，业务逻辑就会与框架绑死，后续换框架或加 CLI 入口都要重写。

### 1.2 技术选型

| 模块 | 选型 |
|------|------|
| Web 框架 | Reflex **0.9.7（锁版本）**，Python 全栈，编译 React SPA |
| 组件包 | `reflex-components-core` / `-lucide`（独立版本，`uv sync --extra web`） |
| 认证 | `reflex-local-auth` 0.5.0 |
| 数据库 | SQLite（WAL 模式），双库：core 业务 + web 认证 |
| 数据模型 | Pydantic（DTO）+ SQLAlchemy 2.0（ORM），显式互转 |
| 部署 | Caddy `reverse_proxy` + systemd（五期，未实施） |
| 包管理 | `pyproject.toml` 统一打包（无 PYTHONPATH hack），`uv` + `uv.lock` |

### 2.1 CRUD 模块六件套

`player` / `team` 采用完全一致的模式，新增 CRUD 模块照抄（见 [07-开发流程](07-开发流程.md) §3）：

| 文件 | 职责 |
|------|------|
| `models.py` | Pydantic DTO：`XxxBase` / `XxxCreate` / `XxxUpdate` / 实体 + 校验器 |
| `store.py` | SQLAlchemy repository；DTO↔ORM 转换在 store 边界 |
| `service.py` | 业务逻辑（唯一约束、ID 生成、筛选）；**写路径在此 bump data_version** |
| `api.py` | **对外唯一读写入口**（facade），CLI 与其他子模块都从这里导入 |
| `cli.py` | argparse 命令行（console_scripts：`xcpc-player`、`xcpc-team`） |
| `exceptions.py` | 模块基础异常 + 子类，供 UI 直接展示消息 |

### 2.2 DTO 与 ORM 分离

领域对象用 **Pydantic DTO**（`models.py`），数据库层另建 **SQLAlchemy ORM 表**（`xcpc_core/db/tables.py`），两者显式互转。

- 理由：ORM 实例渗进 service 层会把 session 生命周期问题扩散各处（detached instance、懒加载越界），也污染业务校验。
- 收益：service 层可单测、事务边界清晰（对 SQLite 锁行为也是加分项，见 §5.2）。

## 3. 数据流

```
data/raw/（人工投放 + import 写回归档，可 diff、可进 Git）
        │
        ▼ import（xcpc_core.importer.*：raw 归档 + SQLite 双写）
        ▼ SQLite（data/db/xcpc.db，运行时数据源）
        ▼ Rating 事件生成（rating.events）→ 计算（rating.engine）
        ▼ 榜单聚合（board，data_version 进程内缓存）
        ▼ Reflex 页面（State 直调 core API）
```

- 数据流**单向**：`raw → DB`；反向只产出备份，不回写 raw
- 原 `data/processed/` 中间层已废弃（职责由 SQLite 取代）
- 榜单不再预生成文件矩阵：筛选条件是服务端 state var，切换即重算（`mode × period × data_version` 为缓存 key）

| `standing` | 自增 | FK contest；`team_id`（solo 为空）；award/solved/penalty/score | ✅ |

**派生表与运维表**：`ratingevent` 可由 Contest/Standing/OJ* 整表重建，不作为事实来源；`meta` 单行表由写路径 bump（见 [04-Rating与榜单](04-Rating与榜单.md) §7）。

### 4.3 建表与迁移

- **开发期**：`Base.metadata.create_all(engine)`（`xcpc_core/db/session.py`）；schema 稳定后引入 alembic（⬜ 未引入）。
- **一次性灌数据**：`uv run python -m xcpc_core.db.migrate` —— 读 `raw/players/roster.json`、`raw/teams/roster.json`、`raw/formal/*.json`，**幂等**（按主键 upsert），现有 ID（p001/t001）原样保留。
- 引入 alembic 时：`env.py` 导入 `xcpc_core.db.base`（含全部表）；注意 alembic 只能发现 env.py 实际 import 的模型。

## 5. SQLite 并发与运维

### 5.1 三件事同时做到，缺一不可

SQLite 允许多个并发读，但**同时只能有一个写**。要在 Web 场景下不报 `database is locked`：

| # | 措施 | 作用 |
|---|------|------|
| 1 | **WAL 模式** | 读不阻塞写（持久化，设一次生效） |
| 2 | **busy_timeout** | 撞锁时等待重试而非立刻抛错 |
| 3 | **短事务** | 不在持有写锁时做慢活（xlsx 解析、Rating 重算不放写事务） |

**WAL 单独不够**（实测：仅 WAL 不设 timeout，6400 次操作仍 7 次锁错误；WAL + 1s busy_timeout 为 0）。实现见 `xcpc_core/db/session.py`——PRAGMA 挂在 `connect` 事件**逐连接执行**，`journal_mode` 除外（持久化在库文件）。`foreign_keys=ON` 也要逐连接设：SQLite 默认不强制外键。

### 5.2 三个容易踩的坑

- **`check_same_thread=False` ≠ 连接可并发使用**：连接池线程安全，`Session` 对象不是——不要跨线程共享 session。
- **ORM 会让锁问题更严重**：Session 默认在事务中运行，autoflush 会在 SELECT 前先发 DML。DTO/ORM 分离让事务边界更容易看清（§2.2 的附带理由）。
- **长事务是最大的隐藏杀手**：导入解析用 `ImportBatch` 暂存、确认才短事务落库，正是为此。

### 5.3 规模与单进程

- 写操作量级是「admin 偶尔导一场比赛、队员偶尔改 OJ 账号」，WAL + busy_timeout 完全够用；真不够时 `db_url` 换 Postgres，`xcpc_core` 一行不改。
- **单进程约束**：Reflex State 存在进程内存里（按 client token 索引），多 worker 会让同一用户落到不同进程。**不要加 `--workers`**；这同时保证 SQLite 只有一个写进程。

### 5.4 备份

```cron
30 4 * * * sqlite3 /opt/xcpc-rating/data/db/xcpc.db ".backup '/var/backups/xcpc-$(date +\%F).db'"
```

用 `.backup` 而非 `cp`（对正在写入的库安全）；`data/raw/` 已在 Git，本身就是一份可追溯冷备。备份 cron 属于五期（⬜ 未实施，见 [06-部署与运维](06-部署与运维.md)）。
