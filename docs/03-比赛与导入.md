# 比赛与导入

> 定位：**参考 + 待建**。关联：[02-选手与队伍](02-选手与队伍.md) · [04-Rating与榜单](04-Rating与榜单.md) · [05-Web与认证](05-Web与认证.md)

定义**可计入 Rating/积分的数据来源**及其结构。**本系统不爬取数据**，只接收人工或外部导出的文件，完成校验、关联选手/队伍、写入 SQLite。

> 实现状态：**比赛统一化 P-U1 已落地（2026-10-01）**——正式赛 xlsx 导入全链路、统一比赛模型（`tier`/`awardlevel`/`contest` 改造）、积分认证流改挂 contest 均已实现；通用 JSON 导入（P-U3）与 OJ 数据源为**待建**。规格：根目录 CONTEST_UNIFICATION_PLAN.md。

## 1. 统一比赛模型（2026-10-01 起）

「正式赛 / 训练赛 / 积分场次」不再分轨，统一为一个**比赛**实体（`contest` 表）：

| 维度 | 取值 | 说明 |
|------|------|------|
| 赛制 `format` | `icpc` \| `ioi` | 成绩形态：solved+penalty / score |
| 参与形式 `entity` | `team` \| `player` | 认证与积分账本主体 |
| 赛事等级 `tier_id` | → `tier` 表 | 积分系数与排名权重（管理端 `/admin/tiers` CRUD） |
| 计分方式 `scoring` | `formula` \| `award_only` | award_only =「积分只由奖项决定」，强制不进排名 |
| 双开关 | `counts_for_points` / `counts_for_ranking` | 逐场决定进积分流水 / Rating 重放 |
| 申报开关 `allow_claims` | 默认开 | 导入的正式赛关闭（数据由导入通道进入） |

约束（DTO 校验）：`award_only ⇒ counts_for_ranking=False`；计积分的 formula 场次 `max_value ≥ 1`；`contest.id` 禁空白/路径穿越。

配套表：

- **`tier`**：赛事等级（name 唯一、coefficient、sort_order）。初始种子来自 `contest_weights.yaml`（系数 = weight/100）+ 兜底「未分级」；正式赛导入按 `contest_type` → config 标签解析等级（缺失自动按 config 重建）。
- **`awardlevel`**：奖项基线分（gold 100 / silver 60 / bronze 30 / honorable 20）。奖项分 = 基线 × tier.coefficient。
- **积分认证**（`pointsclaim`/`pointsentry`）直接挂在 `contest_id` 上，`pointsevent` 表已删除（历史数据并入 contest，id 形如 `points_{旧id}`）。

数据通道两入口：**管理员导入**（正式赛 xlsx 已实现；通用 JSON 待建 P-U3）与**选手申报**（认证-审核流，见 [05](05-Web与认证.md)）。

## 2. 正式赛导入（formal 通道）✅ 已实现

### 2.1 业务规则

- 只保存**校内相关队伍**的：排名、获奖、解题数、罚时等；同时保存全场参赛总队伍数 `n_teams`（含外校，积分百分位用它）
- 不保存外校队伍明细；`contest_type` 是导入参数，按 config 解析为**赛事等级**（tier），等级决定积分系数与排名权重

### 2.2 比赛元信息（`contest` 表）

关键字段：`id`、`title`、`date`（由它推导 `competition_year`/`season`）、`format`（formal 固定 `icpc`）、`entity`（formal 固定 `team`）、`tier_id`（由 `contest_type` 解析）、`n_teams`、`school_teams_count`、`max_value`（回填 = 成绩最高解题数）、`scoring="formula"`、`counts_for_points=False`、`counts_for_ranking`（沿用归档 `rated`）、`allow_claims=False`、`source_file`（追溯 `raw/formal/…`）。

### 2.3 导入链路（三种入口，共用同一套 service）

| 入口 | 场景 | 说明 |
|------|------|------|
| **一步式** `import_formal_xcpcio_xlsx(path, FormalImportParams)` | CLI / Agent（skill：formal-import） | 解析 → 匹配 → 建档建队 → 写库 → raw 归档，一气呵成 |
| **手动补队** `add_formal_team(AddFormalTeamParams)` | 补录打星队 | award 必须达奖线，否则报错 |
| **Web 五步 staged** `/admin/import` | 三期投产的主路径 | 见 §2.4 |

`FormalImportParams` 要点：`contest_id`、`date`、`contest_type`（必填，→ 解析赛事等级）、`format`（固定 `team_xcpc`，归档用）、`school_organizations`（来自 `school.yaml`，精确匹配过滤本校队伍）、`standings_sheet`/`total_teams_sheet`（xlsx 页签名）、`include_unofficial`。`weight_override` 已废弃（保留字段兼容旧 staged payload，DB 写入不再使用）。

### 2.4 Web 在线导入五步（`/admin/import`）

```
步骤 1  上传          [选择 .xlsx]  [上传]
步骤 2  填元信息      contest_id / 日期 / contest_type（→ 自动解析赛事等级）
步骤 3  解析预览      312 队，本校 8 队，奖牌线自动推算
步骤 4  匹配未识别    「李某某」→ [新建选手 ▼] [p003 李冉曦]
步骤 5  确认写入      [取消]  [确认导入]
```

关键设计（`xcpc_core/importer/staged.py`）：

- **解析结果先落 `ImportBatch`（`status=staged`），确认后才写正式表**——中途关页面不产生半截数据
- 未匹配项由人工逐个决策，替代 `auto_create_players=True` 盲目自动建号
- 确认时**单个事务**写入选手/队伍/比赛（service 层 `commit=False` + 末尾统一 commit），成功后才归档 raw JSON
- 上传文件用安全临时路径，确认/取消/重传时清理；长解析 `@rx.event(background=True)` 不进写事务
- 写 `import.confirm` 审计

API：`stage_formal_xlsx` / `get_import_batch` / `list_import_batches` / `discard_import_batch` / `confirm_import_batch(batch_id, decisions)`。

### 2.5 配套实现

| 文件 | 职责 |
|------|------|
| `xcpcio_xlsx.py` | XCPC.io xlsx 榜单解析（`parse_xcpcio_xlsx`） |
| `awards.py` | 奖牌线推算与获奖分配（formal_medals / percentile 两种阈值源） |
| `weights.py` / `config.py` | 权重表与 school.yaml 读取、赛年/赛季标签 |
| `players.py` | 队员姓名解析与自动建档（`resolve_member_names`） |
| `formal.py` / `formal_store.py` | 一步式导入主流程、raw 归档读写 |

### 2.6 raw 归档

`data/raw/formal/{contest_id}.json` 由导入**写回归档**（可 diff、可进 Git）：含 `contest_id`/`date`/`contest_type`/`weight`/`award_thresholds`/`standings`（每队 `team_id`、`member_names`、`player_ids`、`rank`、`school_rank`、`award`、`solved`、`penalty`、`unofficial`）/`unmatched_players`/`unmatched_teams`。样例：`data/raw/formal/2026_sichuan_provincial.json`。

**重复导入**：同一 `contest_id` 整批替换 standings（最新导入为准）；删除比赛时级联清理 standings（以及派生表 `ratingevent` 中 `{contest_id}#` 前缀的残留行——该表现已无写入方，见 [01](01-架构与数据流.md) §4.2）。

## 3. 校内训练赛（并入统一比赛）

> 统一模型落地后，训练赛不再是独立 `source_type`：**与正式赛同表同入口**，创建时选赛制/形式/等级即可（原 `division` 四档 → tier 标签「全体队员组」等，种子已迁）。成绩数据通道 = P-U3 通用 JSON 导入（待建）或选手申报（积分认证流）。

### 3.1 赛制与成绩形态

| `format` × `entity` | 参赛方式 | 成绩字段 |
|----------------------|----------|----------|
| `icpc` × `team` | `members` 1–3 人 | `rank`, `solved`, `penalty` |
| `icpc` × `player` | 单人 | `rank`, `solved`, `penalty` |
| `ioi` × `player` | 单人 | `rank`, `score` |

原 `division` 档位语义由赛事等级承载：div1+2/div1/div2/div3 已映射为 tier（系数 1.0/0.95/0.7/0.6），管理端可改名调系数。

### 3.2 通用 JSON 导入（✅ P-U3，2026-10-26）

任意比赛数据（训练赛、个人赛、IOI 制）通过 JSON 模板导入，归档落在 `data/raw/contests/`。

**入口**（`xcpc_core/importer/contest_json.py`；facade：`importer.api.import_contest_json`）：

```bash
python -m xcpc_core.importer.cli template --entity team      # 打印模板（team|player|ioi）
python -m xcpc_core.importer.cli import 模板.json --dry-run   # 只校验，不写库
python -m xcpc_core.importer.cli import 模板.json
```

**模板字段**：`contest_id` / `title` / `date` / `format`(icpc|ioi) / `entity`(player|team) /
`tier`（等级名）或 `contest_type`（config 类型 key，二选一）/ `n_teams` / `max_value` /
`scoring`(formula|award_only) / 双开关 / `allow_claims` / `standings[]`。
成绩行：`team_name?` / `members[]`（个人赛恰好 1 人）/ `rank?` / `school_rank?` /
`award?` / `solved?` / `penalty?` / `score?` / `unofficial?`。

**校验（DTO 层前置报错，任何构造路径都绕不过）**：
- 只允许 `icpc×team`、`icpc×player`、`ioi×player` 三种组合（`ioi×team` 无成绩口径）
- `entity=player` 每行恰好 1 人；`entity=team` 每行 1–3 人
- `counts_for_ranking` 场次至少一行有 `rank`；`scoring=award_only` 每行必须有 `award`
- `counts_for_points` 且 `formula` 时 `max_value` 缺省按全场最高分推导
- `contest_id` 拒绝路径穿越；`tier` 与 `contest_type` 互斥

**复用边界**：
- **复用** formal 的姓名解析（`resolve_member_names`：同名歧义 → 未匹配）、建队
  （`resolve_team`：member_key 身份 + 别名合并）、统一比赛映射、tier 解析
- **不复用** xlsx 解析与奖项阈值推算（通用 JSON 由填写方直接给 `award`）；
  staged 五步流程暂未接（见 §3.4）

**归档目录**：新导入写 `data/raw/contests/{contest_id}.json`；`raw/formal/` 继续归正式赛
xlsx。读取侧 `resolve_raw_contest_path()` **新目录优先、旧目录回退**，存量文件无需搬迁；
`db.migrate` 扫描两目录重灌（按 `source_format` 分派映射函数）。

### 3.3 积分入账的两种入口

| 入口 | 触发 | 适用 |
|------|------|------|
| **选手申报 → 审批** | 选手在 `/points` 提交，管理员在 `/admin/points` 审核 | 系统内无成绩、需选手自证 |
| **免认证直录（P4）** | 管理员在 `/admin/points` 选比赛 → 「批量直录」 | 系统内已有权威成绩（正式赛/通用 JSON 导入） |

直录从 `standing` 批量生成 `status=approved` 的认证与积分流水（`points.auto_record` 审计），
与人工审批**共用**同一套积分公式（`_compute_claim_points`）与双账本写入（`_write_entries`），
区别只在起点不经 `staged`。`replace=True` 时先清掉本场此前的直录记录再重建，**不动选手手工提交的认证**。

**P5 防刷上限**：`data/config/points.yaml` 的 `best_n`（缺省 `null` = 不设限）。
设为 N 后，积分榜按**赛年**分组、按单场积分降序取前 N 场（UCup 降序哲学：配额择优，
非先到先得）。团队榜的团队积分与成员队外积分各自择优。

### 3.4 Web 上传入口（✅ 2026-10-26）

`/admin/import` 现在是**两条并列通道**，不是替代关系：

| 通道 | 文件 | 流程 |
|------|------|------|
| 正式赛 xlsx | `.xlsx` / `.xlsm` | 五步 staged：上传 → 元信息 → 解析预览 → 未匹配人工决议 → 确认 |
| 通用比赛 JSON | `.json` | 两段：上传 → 只读预览（匹配情况）→ 确认写入 |

JSON 通道**不需要元信息表单**——`contest_id` / 日期 / 赛制 / 形式 / 等级 / 双开关
全在文件里。预览阶段调 `importer.api.preview_contest_json()`，**只读**：
不写库、不归档、不建档，仅报告每行「已匹配几人 / 将新建几人 / 是否有姓名歧义」。

歧义行会在确认时被跳过，并在预览里用红标 + 提示条告知（建议先去选手管理处理重名或补别名）。
写入成功后记 `import.json_confirm` 审计。

> 未采用 staged 是刻意的：JSON 元信息在文件内，没有「需要人工补填」的环节；
> 唯一需要人工判断的是姓名歧义，而那只影响个别行，不值得为它引入一套 ImportBatch 状态机。

## 5. 统一事件模型（RatingEvent）✅ 已实现（counts_for_ranking 场次）

Rating 计算前，统一比赛转为 `RatingEvent`（`xcpc_core/rating/events.py`）：

```python
RatingEvent(
    event_id="{contest_id}#{standing_id}#{player_id}",
    source_type="contest",           # 统一比赛；oj_* 数据源到位后扩展
    date=..., competition_year=..., season=...,
    contest_type=<tier.name>,        # 赛事等级名（展示用）
    contest_format="icpc",           # icpc|ioi
    player_id=..., team_id=...,
    # rank=原始名次（全省/全场，积分百分位口径）；internal_rank=重排名（Perf 方程口径）
    # n_recorded=入库实体数（重排名分母）
    payload={"rank": 3, "internal_rank": 1.0, "n_recorded": 8, "solved": 8,
             "penalty": 1200, "award": "gold", "entity": "team", ...},
    weight=70,                       # 整数 = tier.coefficient × 100
)
```

- **名次双口径**（D1 定案）：standing 保留全省/全场原始名次；事件生成时按原始名次排序转换为入库实体内部名次（1,2,3…，并列取平均）——原始名次直接喂 Perf 方程会无解，重排名是数学上必须的一步
- **护栏**：可排名实体 < 2 的场次整体跳过；`counts_for_ranking=False` 的比赛不进事件流；award_only 行（rank 为空）天然跳过
- 队伍赛为每名队员生成一条事件（payload 相同、player_id 不同）
- 事件对象由 `build_events_from_contests()` **实时派生**（P-U2 起不落库），派生表 `ratingevent` 当前为空表、无写入方

## 6. 时间标签：赛年与赛季

每场比赛在导入时由 `date` 推导 `competition_year` 与 `season`（`xcpc_core/utils/calendar.py`）：

- **赛年**：9/1 划分（月≥9 属当年，否则属上一年）
- **赛季**：秋学期（9–1 月）/ 寒假（2 月）/ 春学期（3–6 月）/ 暑假（7–8 月）

榜单侧的完整定义见 [04-Rating与榜单](04-Rating与榜单.md) §6。
